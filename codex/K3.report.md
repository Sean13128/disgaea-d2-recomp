# K3 — movie picture-output stall

Fixed output ordering and decoder back-pressure in the shared SDK. **Actual VideoToolbox playback still needs the real-Mac host check:** this sandbox rejects session creation with `-12911`. Full in-game completion below uses explicitly synthetic VT output, not decoded movie pixels.

## Root causes

- `K2-host.jxcoRF/decode.log:76,81,86`: the three errors are backwards presentation timestamps at AUs 36, 38 and 40 (221381→217628, 228889→225135, 236396→232643). They are ordering failures, not VT decode errors. The standalone reader exits on `errors`, explaining its 40-AU/three-input-block run. VT callbacks were forwarded in decode order despite temporal processing.
- Apple's SDK header explicitly permits indefinite callback delay with `kVTDecodeFrame_EnableTemporalProcessing`. Both decode flags are now clear, guaranteeing the output callback completes before DecodeFrame returns. A sorted PTS queue retains the SPS VUI `max_reorder=1` picture; EndSeq drains it. Sparse timestamps still use K2's shared DTS/SEI interpolation. No per-AU VT flush or reference-session reset was added. Final flush errors are no longer suppressed.
- **Reproduced D2's actual stall with synthetic VT:** `K3-mock-game3.log:493`: `output full pictures=2 AUDONE=67 PICOUT=66`. The synchronous HLE returned BUSY when its 64-picture queue filled. D2 cleared its decoder-ready flag and waited for another AUDONE; after the queue drained no accepted AU remained to send that callback. ES release had worked for accepted AUs; demux's eight video slots eventually filled behind the rejected AU. The old logs printed only pictures 1–3 and multiples of 120, so they did not establish a literal three-picture limit.
- `cellVdecDecodeAu` now copies/enqueues AUs to a decoder worker (bounded input queue). Full picture output pauses the worker, retaining the accepted AU until GetPicture wakes it; completion then issues AUDONE and PICOUT. EndSeq queues behind accepted AUs and sends final PICOUTs before SEQDONE. Close cancels/joins the worker safely. Callbacks stay outside queue locks.
- GetPicItem now advances independently of GetPicture, returns EMPTY once all queued metadata has been acquired, and rotates guest metadata storage. This matches RPCS3's firmware handling and allows consumers to fetch metadata ahead without repeatedly reporting the first picture.
